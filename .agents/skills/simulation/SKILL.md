# 시뮬레이션 — 구현 전 가상 운영 검증

> 핵심 질문: **"지금 구현하려는 시스템을 운영자가 실제로 사용한다면, 무엇이 어떤 순서로 잘못되어 어느 데이터와 상태를 망가뜨릴 수 있는가?"**

이 스킬은 정상 입력 몇 개를 테스트하는 방식의 대안이 아니라, **코딩 전 설계의 약점과 누락된 상태를 발견하는 정적·추론 기반 적대적 시뮬레이션**이다. 소스와 계약을 읽고 가상의 실행 순서를 따라가며 결함을 예측한다. 추론은 실운영 성공, 테스트 PASS 또는 결함 재현의 증거가 아니다.

## 0. 적용 범위 및 안전 규칙

- **기본 실행 모드: READ-ONLY / THOUGHT-ONLY.** 코드를 실행하거나 테스트를 돌리거나, API를 호출하거나, DB를 쓰거나, 스케줄러를 켜거나, 파일·GitHub를 수정하지 않는다. 읽기 전용 소스/문서/이력 확인은 허용된다. 사용자가 구체적으로 별도 승인한 경우에만 실행·수정 단계로 전환하며, 시뮬레이션의 결과와 실제 테스트 결과를 분리해 기록한다.
- 소스가 있으면 코드를 우선 열람하고 현재 브랜치·SHA·연관 파일을 확인한다. `HANDOFF.md`만으로 구현되었다고 가정하지 않는다. 증거를 확인할 수 없다면 `미확인`이다. 코드가 없는 신규 기획에는 가상 설계로 분석하되 가정임을 표시한다.
- 우선순위: **사용자 최신 명시 지시 > 승인된 동결 계약·운영 안전 규칙 > 현재 코드의 실제 동작 > 과거 계획 문서/메모 > 시뮬레이션 가정**. 정책 충돌이 발견되면 조용히 수정하지 말고 충돌을 기록한다. 보안·안전·접근 권한은 별도로 유지한다.
- 전체 시나리오 공간을 완전 탐색했다고 주장하지 않는다. 목표는 **치명적 실패 경로의 체계적 발굴과 핵심 불변식의 증거화**다.
- 범용 시스템에도 적용한다. P6/P50 관련 절은 해당 프로젝트일 때만 적용한다.

## 1. 시뮬레이션 착수 — 요구사항과 현실을 따로 고정

다음 7개를 먼저 추출한다. 빠져 있으면 `미확인`으로 두고, 추정해 확정값처럼 사용하지 않는다.

1. **사용자 여정:** 누가 언제 무엇을 실행·중지·재시작·확인하는가. 낮/밤/다음 날/한 달 후까지 하나의 수명주기로 적는다.
2. **최종 성공 정의:** "명령이 종료됨"이 아니라 어떤 영수증·DB 행·커서·출력으로 성공을 증명하는가.
3. **불변 조건:** 절대 바뀌면 안 되는 수치, 동결 정책, 승인 조건, 원본과 중복·재시도 제한.
4. **현재 구현:** 실제 entrypoint, 코드가 작성한 상태와 DB, 외부 서비스 경계, CLI, 스케줄러, 검증된 테스트와 미검증 단계.
5. **상태 주체:** 사용자/계정/작업/요청/API 레인/날짜/저장소/다운스트림 각각의 독립 상태.
6. **외부 의존성:** API 스펙, 인증, 할당량, 네트워크, 파일 권한, 운영자 조작, 타 작업자/에이전트, 시간대.
7. **현실과 설계의 차이:** "해야 한다"와 "현재 코드로 도달 가능하다"를 각각 표시하고, 도달 불가능한 목표부터 검토한다.

증거 태그를 항목마다 붙인다.

- `[F]` 관찰된 코드·문서·현재 결과에 근거한 사실. 출처 파일과 SHA/라인 또는 실행 보고가 필요하다. 문서의 주장이라면 **문서상 주장**임을 명시한다.
- `[D]` 소스/계약으로부터 논리적으로 도출한 결론. 추론 경로를 적는다.
- `[H]` 가정·가능성·미검증 위험. 가정이 깨지면 판정이 어떻게 달라지는지 적는다.
- `[U]` 자료가 없거나 확인 불가. 이를 근거로 PASS를 선언하지 않는다.

## 2. 운영 시스템을 상태 기계로 표현

모든 중요한 흐름을 `상태 → 이벤트 → 사전조건 → 다음 상태 → 영속 증거 → 실패시 복구` 형태로 모델링한다. 단계 이름은 실제 소스 용어에 맞춘다.

최소한 다음 경계를 구분한다.

- `요청 전` / `전송 의도 영속화` / `HTTP 전송` / `응답 수신` / `정제된 응답 Capture` / `RAW 영속 저장` / `관측 투영` / `커서·작업 완료 확정` / `외부 내보내기 확인`
- `최신` / `필수 누락 복구` / `과거 백필` / `중단·쿨다운` / `재시작` / `다음 날 최신 우선` / `과거 이어받기`
- `시작 전`, `진행 중`, `성공`, `명확한 실패`, `결과 불명`, `증거만 저장됨`, `복구 가능`, `영구 차단`, `운영자 판단 필요`

**상태가 저장되는 위치**를 반드시 적는다. 프로세스 메모리, 파일, SQLite, Capture, RAW, Google Sheets, 환경변수는 서로 다른 장애 도메인이다. 하나의 저장소 성공이 다른 저장소의 성공을 뜻하지 않는다.

### 도달 가능성 검증

각 성공 조건에 대해 다음을 역추적한다.

1. 필요한 최종 상태가 무엇인가?
2. 그 상태로 전이하는 함수·작업 생성기·DB 스키마가 실제로 있는가?
3. 어떤 입력과 조건을 만족해야 도달하는가?
4. 루프·호출 제한·날짜 변경·계정 종료·쿼터 대기가 전이를 막지 않는가?
5. 다음 실행에서도 필요한 상태와 커서가 살아남는가?
6. 영원히 대기하거나, 완료 불가능하거나, 실패를 성공으로 오인하는 경로가 있는가?

단 한 단계라도 코드상 연결되지 않으면 `설계상 가능`과 `현재 구현 가능`을 구분하고 `BLOCK` 후보로 지정한다.

## 3. 절대 보존해야 할 불변식 작성

프로젝트별로 추가하되 최소 다음 불변식부터 검토한다.

| ID | 핵심 불변식 | 위반 탐지 질문 |
|---|---|---|
| I-01 | 확인되지 않은 응답을 성공으로 기록하지 않는다 | HTTP 200만 보고 완료로 표시하지 않는가? |
| I-02 | 영속 증거 없이 커서를 전진시키지 않는다 | RAW 실패 후에도 다음 페이지로 넘어가는가? |
| I-03 | 증거가 남은 성공 응답은 가능하면 HTTP 없이 복구한다 | Capture 이후 재시작이 중복 API 호출을 만드는가? |
| I-04 | 결과 불명 HTTP 요청을 자동 재전송하지 않는다 | 타임아웃·프로세스 종료 뒤 같은 요청이 반복되는가? |
| I-05 | 최신화가 과거 백필 진행 지점을 지우지 않는다 | 다음 날 front가 history cursor를 덮어쓰는가? |
| I-06 | 원본·관측·변경 이력은 덮어쓰기 없이 보존한다 | 같은 post_id의 지표 갱신이 예전 관측을 제거하는가? |
| I-07 | 0, NULL, 미요청, 미제공, 오류를 구분한다 | 조회수 0과 누락을 같게 취급하는가? |
| I-08 | 쿼터·승인·권한·경쟁 사용 상태를 우회하지 않는다 | 쿨다운만 지났다고 한도 해제되는가? |
| I-09 | 같은 상태에 대한 중복 실행은 안전하다 | 터미널과 스케줄러가 한 작업을 같이 실행하는가? |
| I-10 | 날짜·시간대·관측시각·게시시각을 구분한다 | 자정 경계에서 어제 작업이 오늘 최신 완료로 잡히는가? |
| I-11 | 부정확한 완료율과 무근거 성공 판정이 없다 | 50/50이 응답 50건인지 게시물·과거 완료인지 구분하는가? |
| I-12 | 실패 격리는 원본 안전성보다 우선하지 않는다 | 한 계정 실패는 격리하되 RAW 파일 손상은 전체 정지하는가? |
| I-13 | 사용자 승인 없는 운영 부작용이 없다 | 읽기·시뮬레이션만 했는데 토큰/API/DB/스케줄을 건드렸는가? |
| I-14 | 내보내기의 체크포인트는 쓰기 확인 뒤 전진한다 | Sheets 실패 후 다음 실행에서 누락을 만드는가? |
| I-15 | 모든 필수 최종 상태에 도달 가능한 실행 경로가 있다 | 생성된 jobs의 상한이 365일 백필 전에 끊기는가? |

**출력에는 불변식별 `보장됨 / 부분 보장 / 위반 가능 / 이미 구조적으로 위반 / 미확인` 판정을 달고, 근거를 연결한다.** 실제 증거가 없으면 `보장됨` 대신 `코드상 방어 조건 존재(실운영 미검증)`로 표현한다.

## 4. 변수 카탈로그: 정상 입력을 넘어 실패를 만든다

분석 대상에 있는 항목을 모두 나열하고, 코드의 분기문·예외·타임스탬프·락·DB 제약·외부 계약으로부터 추가 변수를 추출한다. 하나의 "API 오류"로 뭉뚱그리지 않는다.

### A. 입력·대상

- 대상 0/1/N/초과, CSV 순서 변경, 계정 중복, 누락·이름 변경·삭제·비공개·권한 상실, 국가 불일치, 게시물 없는 계정
- 텍스트 인코딩·특수문자·빈 문자열·매우 긴 캡션·중복 media ID·예상 밖 media type·캐러셀 부분 반환
- 오래된 로스터 vs 실행 중 새 로스터, 계정 ID 재사용·변경, 동일 게시물의 서로 다른 계정 귀속

### B. API 응답·인증·할당량

- HTTP 200·204·400·401·403·404·429·5xx, 연결 끊김, 소켓 타임아웃, 요청 전 실패 vs 전송 후 응답 불명
- Graph 오류 코드/서브코드 차이, 페이징 커서 무효·만료·누락·반복·변조, `next`는 있으나 게시물 0개
- 사용량 0/84/85/100/미수신/형식 오류; 헤더만 정상·본문 오류, 응답 200 후 쿼터 85 이상
- A/B/C 중 하나만 인증 오류, 레인 간 쿼터 공유, 경쟁하는 다른 수집기, 토큰 만료·교체
- 배치라면 외부 HTTP 성공 + 내부 하위 요청 일부 실패, 응답 순서/개수 불일치, 전체 배치 성공 오인

### C. 시간·스케줄

- 23:59:59 KST 시작 후 00:00:01 응답, 관측 시각과 작업 일자 불일치, 날짜 변경 중 백필 실행
- 쿨다운 시작 시점과 종료 시점, 시스템 재부팅 뒤 시간 오차, 시계 역행, 수동 시간 변경
- n8n 중복 인스턴스, 동일 워크플로 중복 등록, 수동 최신화와 자동 과거 실행 충돌

### D. 상태·커서·저장

- 커서 없음/NULL/만료/삭제/다른 계정의 커서/역방향 이동/응답에 같은 커서 반복
- SQLite 정상/잠김/WAL 잔류/용량 부족/읽기 전용/스키마 변경/파일 손상/권한 거부
- Capture만 있음, RAW만 있음, 작업 완료만 있음, 오브저베이션만 있음, 서로 다른 request_id·capture_id
- 새 날에 초기화된 jobs가 이전 day's 미완료 history 상태를 덮어쓰기, 완료 판단만 있고 경계 시각 증거 없음
- 원본 URL 만료, 게시물이 삭제되어 중간 페이지가 축소, 필드가 변경되거나 제공되지 않음

### E. 사용자의 운영 행동

- Ctrl+C, 프로세스 강제 종료, PC 종료·재부팅·절전·네트워크 변경, 반복 엔터로 두 번 실행
- 잘못된 경로·워크스페이스·명령 인수, 백업에서 복원, 과거 모드 중 최신 모드 시작
- 여러 브랜치/워크트리에서 같은 DB 접근, Git pull로 스키마·로직 변경 중 재실행

### F. 다운스트림·해석

- Google Sheets 쓰기 성공/부분 성공/응답 불명, upsert 중복, observation_id checkpoint 선전진
- 데이터 수집 시각을 게시 시각으로 오인, 과거 게시물의 현재 좋아요를 과거 좋아요로 오인
- Reels 실제 조회수 0 vs 제공 안 됨, 특정 필드 관측 누락, 반응 변화의 첫 관측 덮어쓰기
- 대시보드 새로고침이 수집·태깅을 다시 호출하는 부작용

### G. 변경·협업·배포

- 서로 다른 브랜치와 SHA의 인터페이스 차이, 문서에는 있으나 코드에는 없는 함수/옵션
- 테스트용 mock이 실 Meta 오류·파일 ACL·운영 권한을 감추는 경우
- old DB와 새 코드의 마이그레이션, 롤백 후 구버전의 새로운 데이터 해석 불가
- CI의 부분 PASS vs 전체 실패, 불완전한 인수인계, 사용자 승인 없이 정책 재설계

## 5. 사고 실험의 기본 단위

시나리오마다 아래 형식을 사용해 **이벤트 순서**까지 구체적으로 적는다.

```text
시나리오 ID: SIM-###
전제/증거 등급: [F]/[D]/[H]/[U]
시작 상태: (모드, 계정, 날짜, 커서, 레인 쿼터, request 상태, Capture, RAW, job 상태)
고장 주입 위치: 저장/호출/날짜 전환/중복 실행 중 정확히 어느 순간인가
이벤트 순서: E1 → E2 → E3 → ...
기대 안전 동작: ...
현재 소스상 예상 전이: ... (파일/함수/분기 + SHA)
깨질 수 있는 불변식: I-##
실패 결과: 원본 유실 / 누락 / 중복 호출 / 영구 대기 / 잘못된 완료 / 보안 노출 등
최소 수정·대안: 재설계 대신 최소 방어·복구 경로를 우선
수정하지 않을 경우 운영 우회책: ... (안전한 경우에만)
판정: BLOCK / FIX-BEFORE-LIVE / VERIFY-LATER / COVERED / UNKNOWN
실제 테스트 전환 시 필요한 합성 fixture·오라클: ...
```

단일 이벤트의 예: "커서 만료". 복합 시나리오의 예: "23:59에 과거 요청 발송 → 응답 수신 후 RAW 전에 PC 종료 → 00:01 새 최신 작업 시작 → 과거 커서 만료 → 다른 레인 85%". 후자에서 정상 반환이 가능해 보이더라도 **어떤 증거가 어디에 남았는지**로 판정한다.

## 6. 조합 폭발을 통제하는 선택 규칙

모든 변수의 전체 곱집합은 불가능하다. 다음 순서로 선택한다.

1. **핵심 불변식마다 반드시 하나 이상** 위반을 시도하는 부정 시나리오를 생성한다.
2. 데이터 무손실·중복 API 방지·커서 연속성·안전 게이트는 **각 영속성 경계의 직전·직후** 종료를 모델링한다.
3. 독립 변수는 2-way(pairwise) 조합으로 폭넓게 스캔한다. 서로 영향 주는 변수는 3-way 이상으로 심화한다. 정확한 전수 커버리지 보장을 주장하지 않는다.
4. 이전 실제 사고, 코드에서 복잡한 예외 분기, 문서/코드 불일치, 인터페이스 접점, 사용자가 매일 반복하는 작업에 우선순위를 높인다.
5. 가장 위험한 시나리오 하나가 발견되면 같은 근본 원인을 공유하는 **변형 시나리오 3개**를 추가하고 공통 수정으로 닫히는지 확인한다.
6. 중요 조건이 모두 안정적일 때만 저위험 UX/성능 변수를 검토한다.
7. 하루 운영뿐 아니라 **다음 날·다음 주·중간 업데이트·복구 후**를 포함한다.

### 최소 고장 주입 절단면(Thought-only)

다음 각각에서 즉시 종료된 것으로 가정하고 무엇이 영속 저장되었는지 확인한다.

1. 요청 의도 기록 전
2. 의도 기록 후·HTTP 전
3. HTTP 전송 후·응답 확인 전
4. 응답 확인 후·Capture 기록 전
5. Capture 영속화 후·RAW 기록 전
6. RAW 영속화 후·작업 완료/커서 전진 전
7. 커서 저장 후·UI/CLI 성공 출력 전
8. 다운스트림 저장 후·동기화 체크포인트 확정 전

**특히 3·4번은 응답 여부가 불명확할 수 있다.** "무조건 재시도하면 된다"는 복구 전략이 아니다.

## 8. 위험도·수정 의사결정

증거를 확인한 뒤 위험을 다음처럼 평가한다. 높은 위험이 있다고 해서 임의의 정책 변경 권한을 얻는 것은 아니다.

- **P0 / BLOCK:** 원본 데이터 유실·오염, 확인되지 않은 HTTP 재요청, 인증정보 노출, 승인·쿼터 위반, 복구 불가능한 상태, 필수 성공 경로 부재. 운영 승인 이전 해결 또는 안전하게 기능 차단.
- **P1 / FIX-BEFORE-LIVE:** 의도한 운영 사이클이 중단됨, 백필 진행 불가, 잘못된 완료 선언, 영속 커서 충돌, 재시작 시 작업이 영구 정체될 가능성. 최소 수정·오프라인 검증부터.
- **P2 / VERIFY-LATER:** 복구 가능한 단일 계정 문제, 격리된 후처리 문제, 주요 계약과 독립적인 속도 개선. 명시적으로 유예 가능.
- **P3 / OPTIONAL:** 기능·데이터 안전성에 영향이 작은 UX/성능 개선.

불확실성은 심각도와 별도로 표시한다: `높음/중간/낮음`. **위험이 큰데 근거가 부족하면 `UNKNOWN-BLOCKER`**로 취급한다. 분석하지 않은 조건을 `문제없음`으로 분류하지 않는다.

선택 가능한 수정안은 최대 3개만 비교하고 **최소 수정 / 영향 범위 / 기존 데이터 호환 / 운영 중단 / 후속 검증 비용**을 제시한다. 원본 DB 초기화·전면 재설계·쿼터 우회는 기본 대안으로 제시하지 않는다.

## 9. 시뮬레이션 종료 조건과 필수 보고서

가상 검증은 다음 산출물로 끝낸다. 긴 상황에서도 우선순위를 유지한다.

1. **결론 3줄:** 지금 구현 가능한 것 / 코드상 불가능하거나 미검증인 것 / 가장 위험한 병목.
2. **시스템 경로:** 실제 사용자 1회 실행부터 다음 날 재개까지의 상태 전이 도식.
3. **소스 기반 변수·불변식 목록:** 누락·충돌·입력 불명확성을 드러내고 추출 근거를 적는다.
4. **우선순위 위험 TOP 10:** 시나리오 ID, 현재 근거, 예상 실패, 최소 수정, 운영 차단 여부.
5. **복합 실패 타임라인 3~5개:** 최소 하나는 날짜 변경 + 프로그램 종료 + 커서 이상을 결합한다.
6. **상태/전이 커버리지:** 확인한 상태와 경계, 확인하지 못한 상태를 분리한다.
7. **구현 순서·승인 필요사항:** 위험 제거에 필요한 최소 작업 순서. 승인 없는 코드/운영 변경은 수행하지 않는다.
8. **테스트 설계로 변환:** 각 P0/P1 위험을 실제 후속 오프라인 테스트 입력·기대 결과·PASS 판정 기준으로 바꾼다. **실행하지 않았다면 `NOT RUN`**으로 표시한다.
9. **판정:** `DESIGN BLOCKED` / `READY FOR IMPLEMENTATION WITH OPEN RISKS` / `READY FOR OFFLINE TESTING` 중 하나. 이들은 **실운영 사용 승인이나 live 검증 완료 상태가 아니다.**

# 시뮬레이션 보고서 — {프로젝트/기능}

## 10. 작업자 역할과 재사용 규칙

- **설계자/감독자:** 구현 착수 전 완성된 사용자 여정을 끝까지 가상 실행한다. P0/P1과 가정·불확실성을 작업자에게 명확히 전달한다. 범위 밖 재설계는 승인 전 제안만 한다.
- **구현자:** 자신이 수정하려는 함수·스키마·CLI를 기준으로 영향받는 시나리오를 찾아 설계 전이의 빈칸을 메운다. 수정 전후 시뮬레이션을 비교한다.
- **검수자:** 구현자가 주장한 PASS가 오프라인 실행 증거인지, 소스 기반 추론인지, 실 Meta/운영 증거인지 분리해 검증한다.
- **채팅방/작업자 교체:** 브랜치·SHA, 미해결 시나리오 ID, 가장 최근 보장 불변식, 다음 합성 테스트를 인계한다. 다른 SHA에 대한 오래된 결과를 자동 승계하지 않는다.
- **재발:** 동일 실패·수정 재시도 1~2회 후에도 막히면 같은 패치를 반복하지 말고 상태 모델과 가정을 갱신한다.

## 11. 작업 시작 전에 스스로 묻는 마지막 질문

- 처음부터 끝까지 **실행 가능한** 상태 전이인가, 아니면 문서에만 존재하는 경로인가?
- 정상 흐름이 아니라 **각 영속화 경계에서 전원이 꺼지면** 어떻게 되는가?
- 안전하게 중단해도 **다음 날 같은 곳에서 이어지는가**?
- "성공"이라고 말할 때 실제로 **어떤 저장 증거**가 존재하는가?
- 한 가지 변수만 바꿨는가, 아니면 **시간 × 상태 × 실패 × 복구**를 동시에 생각했는가?
- 가장 약한 전제가 틀렸을 때 **어디부터 잘못된 완료 판정**이 전파되는가?
- 추론을 테스트 결과로 과장하지 않았는가? **아직 확인하지 않은 조건**은 무엇인가?

이 질문에 답할 수 없으면 문제를 없는 것으로 처리하지 않는다. 해당 부분을 `UNKNOWN`으로 남겨 다음 증거 수집 또는 구현 검증 단계에 연결한다.
