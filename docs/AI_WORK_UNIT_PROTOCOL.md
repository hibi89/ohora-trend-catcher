# P6 개발·검증 운영 원칙

이 문서는 기존 작업단위(N-unit) 운영 규칙을 대체한다. 과거 사건·커밋·테스트 기록은 삭제하지 않고 이력으로 보존한다.

## 진행 방식

- GitHub 최신 HANDOFF.md → STATUS.md → AGENTS.md → REQUIREMENTS.md → 실제 코드 및 CI를 확인하고 개발을 재개한다.
- 다음 미완료 기능을 실제로 구현하고, 필요한 회귀 테스트를 수행한 후 개발 브랜치에 반영한다.
- 유효한 기능·테스트·복구 작업을 우선한다. 임의의 작업단위 개수, 단위별 커밋 수, 숫자 목표 및 주기별 보고 의무를 사용하지 않는다.
- 주요 기능 완료·중단·인수인계 시 STATUS.md, HANDOFF.md, 사건 장부(해당 시), 중앙 BOOK.md를 갱신하고 GitHub 재조회로 확인한다.
- 실패·중요 설계 변경은 docs/P6_TROUBLESHOOTING_LEDGER.md에 원인·근거·대안·검증 결과를 기록한다.
- 성공은 커밋, 오프라인 테스트, CI, 실운영을 구별해 보고한다.

## 변경 승인 경계

실 Meta API 호출, 운영 DB·원본 데이터 변경, main 병합, 운영 스케줄러 활성화, 동결 설계 변경은 별도 명시적 승인 없이는 실행하지 않는다. 3 API·limit=4·2라운드·원본 불변 정책을 유지한다.

## 이전 문서와의 관계

과거 STATUS.md/HANDOFF.md 및 Git 이력의 N단위·12단위·작업단위 표현은 당시 수행 이력일 뿐 현재의 작업 지침이 아니다. 신규 AI 작업자는 본 문서를 현재 진행 기준으로 사용한다.
