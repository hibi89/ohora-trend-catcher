# AI 작업단위 운영 프로토콜 (N-unit)

> 적용: OHORA Trend Catcher p6 개발 및 인수인계. 작업 주기 N은 사용자가 정하는 가변값이며 기본적으로 고정하지 않는다.

## 1. 작업단위 정의

**1작업단위(Unit)는 하나의 독립적인 코드 변경 또는 검증 작업이다.**

기능 전체를 완성해야만 1단위인 것은 아니다. 오류 수정, 방어 로직 추가, 회귀 테스트 작성도 각각 독립적인 1단위가 될 수 있다. 단, 실제 GitHub 저장소에 유효한 변경을 반영해야 하며 단순 분석·계획·문서 정리만으로 완료를 선언하지 않는다.

작업단위의 경계는 **식별 가능한 변경 목적**으로 정한다. 커밋 수를 늘리기 위한 인위적 분할은 금지한다.

## 2. N단위 실행·보고 사이클

사용자가 `ㄱ`을 입력하면, 현재 합의된 **N단위**를 실행한다. N은 고정 숫자가 아니며 사용자가 변경할 수 있다. 기존 대화에서 설정한 N이 있으면 이를 따른다. 값이 정해지지 않은 새 작업 세션에서는 임의의 숫자를 사실처럼 가정하지 말고 확인한다.

1. 작업 브랜치, 최근 커밋, CI 상태, 동결 설계 및 권한 범위를 확인한다.
2. 우선순위에 따라 N개 작업단위를 순차 실행한다.
3. 각 단위에서 유효한 변경을 커밋하고 SHA를 기록한다.
4. 가능한 테스트 및 CI 결과를 확인한다. 실패가 확인되면 새 기능보다 원인 분석·복구를 우선한다.
5. N단위 완료 후 `STATUS.md`, `HANDOFF.md`, 중앙 `hibi89/project-book/main/BOOK.md`를 최신화한다.
6. 변경 내용, SHA, 검증 결과, 차단 요인, 다음 우선순위를 한 번 보고한다.

**문서 최신화는 원칙적으로 N단위에 포함하지 않는다.** 중대한 차단·보안·승인 필요 사항이 발생하면 N단위 완료를 기다리지 않고 즉시 보고한다.

## 3. 예시 (각각 독립된 단위일 수 있음)

- Unit A: History 커서 중복 감지 로직 수정
- Unit B: 커서 변조를 탐지하는 회귀 테스트 추가
- Unit C: RAW receipt와 체크포인트 일치 여부 검증 강화

같은 기능 영역의 작업도 변경 목적이 구분되면 별도 단위가 될 수 있다. 다만 작은 문구 수정이나 실질적으로 동일한 작업의 반복을 단위로 부풀리지 않는다.

## 4. 검증 상태를 구분하여 보고

- **구현 완료:** 코드 변경이 GitHub에 커밋됨
- **테스트 통과:** 해당 테스트의 성공을 실제 확인함
- **CI 통과:** 해당 커밋의 GitHub Actions 성공을 실제 확인함
- **미검증:** 실행 결과를 확인하지 못함

커밋 완료만으로 테스트·CI 통과를 주장하지 않는다. 이전 커밋의 CI 성공을 최신 커밋의 성공으로 전용하지 않는다.

## 5. 승인 경계

사용자의 `ㄱ`은 합의된 범위의 N단위 개발 진행 승인이지 운영 변경 승인과 같지 않다. 별도 명시적 승인 없이 다음을 하지 않는다.

- Meta API 실호출
- 운영 DB 또는 보존 대상 원본 데이터 변경
- main 브랜치 병합
- 동결된 최종 수집 설계 변경
- 운영 스케줄러 활성화 및 배포

현재 p6의 동결 설계, RAW 불변성, 3 API·limit=4·2라운드 제약은 계속 적용한다.

## 6. 목적

**N단위는 보고 주기이며 개발 목표 자체가 아니다.** 작업의 목적은 작은 검증 가능한 변경을 누적하면서 회귀 위험을 통제하고 실제 시스템 완성도를 높이는 것이다.
