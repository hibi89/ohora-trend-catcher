## 1. 질문과 결론

- 질문: Google Sheets 저장 한도는 전체 구글 계정 합산인가, 스프레드시트 파일당인가? 꽉 차면 새 파일을 자동 생성하여 이어 쓸 수 있는가?
- **확인 결과:** Google Sheets의 셀 한도는 **스프레드시트 파일 단위로, 파일 안 모든 탭의 할당 셀 합산**이다. Google 공식 안내(2026-09 일반 출시)는 기존 1,000만 셀에서 **파일당 2,000만 셀**로 확대되었다고 명시한다. Google Drive 도움말은 **2,000만 셀 또는 100MB**를 안내한다. 셀 한도는 '행 수'가 아니다.
- 예: 20열 × 약 100만 행 = 약 2,000만 셀(다른 탭·헤더·할당된 빈 행/열·파일 크기 한도를 제외한 이론값).
- **설계상 가능:** 한도에 접근하면 n8n 또는 별도 동기화 워커가 Google Sheets API로 새 스프레드시트를 생성하고 다음 데이터부터 이어 쓰게 할 수 있다. 실제 자동 생성·회복 흐름은 미구현/미검증.
- 파일 개수를 늘려도 무제한 보장은 아니다. Drive 저장공간·파일 수·Sheets API 할당량·대용량 읽기/쓰기 성능·권한 제한이 남는다.

**공식 출처**

- https://support.google.com/drive/answer/37603?hl=ko

## 2. 권장 구조 (기존 수집 엔진과 독립)

```text
Meta API A/B/C → 기존 RAW/Capture/SQLite (모든 관측·버전·영수증 보존)
                    │ 읽기 전용 검증 export
                    ▼
             n8n 동기화 워커
             ├─ 파일 등록부(spreadsheet_id/국가·파티션/상태/용량 추정)
             ├─ 관측키 전역 색인(observation_key → 파일/탭/행 또는 존재 상태)
             └─ 확인된 마지막 동기화 체크포인트(원본 DB별 독립)
                    │
                    ├─ OHORA_KR_001 → OHORA_KR_002 → ...
                    ├─ OHORA_US_001 → OHORA_US_002 → ...
                    └─ OHORA_JP_001 → OHORA_JP_002 → ...
                          ▼
                Google Sheets 조회·대시보드
```

- **SQLite/RAW만 원본(source of truth).** Sheets는 downstream 활용/공유용 복제본이고 수집 커서·원본 영수증을 대체하지 않는다.
- 국가별 파일 분리는 **선택 가능한 파티셔닝 예시**다. 한 파일 순차 분할도 가능하며 최종 탭/파일 구조는 별도 승인 후 확정한다.
- 기존 `raw_v2/three_api_sheets_export.py`와 `docs/P6_N8N_SHEETS_EXPORT_CONTRACT.md`의 검증된 영수증·NULL·순서·커서 계약 유지.
- `observation_key = request_id:post_id`는 관측 1건의 멱등 키다. `post_id`만으로 관측 이력을 덮어쓰지 않는다. `reels_view_count=0`과 `null`을 구분한다.
- F5/화면 조회는 보존된 데이터를 **읽기만** 하며 Meta 재수집·AI 재분석을 트리거하지 않는다.

## 3. 자동 교체 조건 — 제안값, 확정 설정 아님

1. 활성 스프레드시트의 **전체 탭 할당 셀 수**와 남은 적재 공간을 확인하고, 다음 배치의 추가 열×행을 예산에 포함한다. 실제 쓰기 가능 공간을 확인하지 않고 값이 있는 셀만 세어서는 안 된다.
2. **안전 여유안: 사용률 90% 수준에서 새 파일 준비/교체**를 제안한다. 숫자는 테스트 후 조정할 수 있으며 현행 P6 동결 상수와 무관하다.
3. **셀 한도와 100MB 파일 제한 중 먼저 닥치는 제한**을 고려한다. 문자량 기반 용량을 정확하게 예측하기 어렵다면 더 작은 배치·여유 버퍼·API 실패 감지를 적용한다.
4. 기존 파일이 꽉 차거나 다음 배치를 수용하지 못하면 후속 파일(`_002`, `_003`)을 **생성 → 등록 → 쓰기 검증**한다. 기존 파일·기록은 보존한다.
5. 파일별 헤더·컬럼 스키마·국가/기간 범위·파일 ID·생성시각·기록 상태를 등록부에 남겨 전체 파일을 통합 조회 가능하게 한다.
6. Sheets 하나가 너무 커지면 UI/API가 느려질 수 있으므로 실제 부하 테스트에서 조기 회전이나 기간 단위 파일 분할을 검토한다.

## 4. 누락·중복 방지 (실제 구현의 필수 합격 기준)

- 현재 export 배치의 `after_id`/RAW DB 식별자와 `observation_key`를 유지한다. P50과 294, DB 스냅샷 간 체크포인트를 공유하지 않는다.
- 이전 파일에 이미 기록한 `observation_key`가 재시도/재관측 때 새 파일에 중복 추가되지 않도록 **여러 파일에 걸친 전역 인덱스/조회 전략**을 갖춘다. 파일 안에서만 upsert하면 회전 경계 중복을 못 막는다.
- 파일 생성 직후 네트워크가 끊겨도 무한 재생성되지 않도록 생성 요청 ID/파일 등록부에 pending→active→closed 등 영속 상태를 둔다. 미확정 쓰기는 먼저 읽어 재조정하고 무조건 재발송하지 않는다.
- **모든 대상 행의 Sheets 쓰기 및 재조회 확인 이후에만** 외부 체크포인트를 전진한다. 부분 성공/응답 불명/RAW 영수증 누락 시 같은 커서로 멈추고 안전 재개한다.
- 등록부/체크포인트는 n8n 측 별도 영속 저장에 둔다. 원본 운영 RAW DB에 테이블을 무단 추가·변경하지 않는다.
- 동시 실행·중복 트리거를 방지하기 위해 파일 분할과 체크포인트 확정 구간은 단일 동기화 소유자/잠금으로 직렬화한다.
- API 속도 제한/네트워크 오류는 제한된 백오프 및 운영자 알림으로 처리하고, 불명확한 쓰기 결과는 멱등 조회 후 복구한다.
- 오래된 파일 삭제·이동·접근 정책 변경은 사용자 별도 승인 없이는 실행하지 않는다.
